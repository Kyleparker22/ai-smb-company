# Runtime coverage is a distinct eval lane from agent-output quality

- **Source:** Eval review 2026-07-12 (week of 07-06→07-12). Every agent output graded clean (19 outputs, 0 fails), yet the week's real failures were all *below* the agent layer: the watchdog's own timer self-outage (07-07→09, 3 days no monitor), crm-autolog's 07-10 no-fire, and a $24.49 Hostinger failed-payment SPOF. Scoring only the output scoreboard would have reported "sixth clean week" and buried the fact that the OS had no monitor for 72 hours.
- **Pattern:** Agent-output quality and runtime coverage are two independent lanes. An agent can produce a flawless, honestly self-diagnosing artifact *about* a runtime failure (Jim surfacing Hostinger; the watchdog back-checking its own outage) — the output is a 12/12 and the runtime is on fire at the same time. Conversely, a timer no-fire is not the agent's judgment failing; it's systemd/host, owned by the Founder/platform. Collapsing the two lanes into one score corrupts both directions: a clean scoreboard papers over a coverage gap, and a coverage gap unfairly down-scores an agent that reported it correctly.
- **Implication (checklist):** (1) Grade output-quality on the six dimensions as usual. (2) *Separately* enumerate runtime-coverage events — timer no-fires, silent misses, billing/host SPOFs — and route each to its real owner (agent defect → the agent; timer/host → the Founder/platform). (3) A **monitor's own outage is the highest-severity coverage item**, because it's the one gap the monitor structurally cannot cover (a monitor can't share its target's failure mode). (4) Runtime-coverage failures do **not** reset an autonomy streak for a tracked *action* (calendar/gmail/instantly) — different failure domain — unless the action itself misfired. Keep the lanes separate in the streak ledger too.
- **Audience:** Kolby (grading); the watchdog loop (Atlas); the Founder/platform (Kemba) as the owner of the coverage lane.
