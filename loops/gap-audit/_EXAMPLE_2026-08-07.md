# Gap Audit — 2026-08-07 (second run)

> The negative-space review (`processes/gap-audit.md`), run for the first time since **2026-06-12** — 56 days, against a cadence of "monthly + at every major build milestone." The audit designed to catch what's absent was itself absent. Triggered by the Founder in session, not by Brett or a timer. Method: all three sweeps against a real repo scan, plus a fourth sweep this run argues should become standing. Confidence noted per finding.

## Headline

**The June verdict has inverted.** In June the OS was strong at the top of the funnel and weak at the commercial edges. Since then all four June gaps were built — proposal/SOW, payment rail, offboarding, weekly readout — and 93 decisions, 28 timers, 18 frontier offerings and three client engagements were layered on top.

The gaps are no longer *product* gaps. They are **activation gaps and liveness gaps**: things that exist as artifacts but were never switched on, and things that fail silently because nothing watches for absence. Restated as one sentence — **the OS has stopped being unable to do things and started being unable to notice things.**

The single most consequential finding: **the runtime alarm cannot detect the failure that has actually happened three times.** It watches for FAILED runs; a runtime that simply stops running writes no FAILED line, so the alarm reports "all clear" forever. It has been reporting all clear through eight days of darkness.

## Sweep 4 — **the observability of absence** (proposed as standing)

June's audit asked what the *client* can't do. This run adds the inverted question the OS keeps failing: **what can the OS not notice?**

### 🔴🔴 The alarm watches for failure, not for silence

`runtime/runtime-alarm.sh` is well-built and correctly reasoned — pure shell, no API calls, so it survives a dead credit balance. It was written *specifically* to catch the June 16–18 credit death. But read what it does:

> it scans each loop's run log for the most recent status; **if the latest run FAILED** … it posts to Slack.
> `[ -z "$alerts" ] && { echo "[alarm] all clear — no new FAILED runs."; exit 0; }`

**A loop that never runs never writes a FAILED line.** If systemd stops firing, the box is off, the repo lock jams, or `runtime/.paused` is present, the alarm iterates over stale logs, finds no *new* failure, and reports **"all clear"** — every hour, indefinitely. Silence is indistinguishable from health.

This is not hypothetical. Org API spend collapsed to **$0.83 across 08-01→08-06** against an ~$8/day baseline, the last model-driven artifact is **sadie-intent 08-04**, and `open-loops`/`inbox-triage`/`initiative`/`melanie-briefing` all stop at **07-29/07-30**. Roughly eight days dark, and the alarm's design guarantees it said "all clear" through all of it. *(high confidence — the failure mode is visible in the source, not inferred.)*

**Two further layers of the same hole:**
- The alarm posts to Slack via `SLACK_ALARM_WEBHOOK` in a gitignored host-local env file. Whether it is configured **cannot be verified from this repo** — and unconfigured, the script's self-check path silently sends nothing.
- `loops/_runtime/` (the log directory the alarm reads) is gitignored and **empty in this clone**. The evidence needed to audit the alarm is invisible to every surface except the box itself.

**The fix is a heartbeat, not a better alarm.** An alarm inside the runtime cannot report the runtime's absence. What's needed is either (a) an off-box check that expects a signal and shouts when it doesn't arrive, or (b) a human-visible staleness indicator that reads committed artifact dates and does not depend on the runtime being alive. **(b) was built this session** — the *System* lane of The Board computes days-since-last-artifact per loop from git, so eight days of silence is now visible at a glance. (a) remains open and needs the owner Sweep 2 says doesn't exist.

### 🟠 the Founder has no single view of work state — *this audit's origin*

This run exists because the Founder said: *"I feel like we have so much going on… I want an easy way to see everything so I can see what still needs to be worked on."* That is a gap-audit finding in its own right, and the scan confirms it: the answer was spread across **eight surfaces** — `loops/open-loops/` (9 days stale), `loops/gap-audit/` (56 days stale), `launch-gate.md`, `counsel-gates.md`, `crm/_backlog.md`, `offerings/_frontier-roadmap.md`, `processes/automation-roadmap.md`, and an **empty** `dashboard/todo.json`. HQ's four views showed *state*, never *work remaining*.

The pattern: **yourco builds inventories faster than it builds indexes.** Every new workstream adds a tracker; nothing aggregates them; the founder becomes the join. *(high confidence — closed this session by The Board.)*

## Feed-forward

- **The pattern behind this run's gaps has moved.** June: *"gaps cluster where money moves and where clients leave"* — built by a builder optimizing the product, not a commercial operator optimizing the deal. August: **gaps cluster where something must be *switched on* by a human, and where something must be *noticed* by a machine.** The OS now reliably produces artifacts; it does not reliably produce activation or attention. Written to `learnings/ops/`.
- **A tracker is not a mechanism.** Three of this run's findings (counsel gates, OtherVenture, payments) are items where an artifact was created *to track the gap* and the gap then sat still. Creating the tracker felt like progress. Next audit should explicitly ask, per tracker: **has its top row changed since it was created?** If not, the tracker is the gap.
- **Cadence enforcement.** This audit is 56 days late against a monthly cadence and had to be human-triggered — the same class of failure as Sweep 4. There is a `gap-audit` folder but **no `gap-audit` timer or prompt** in `runtime/`. Brett owns the audit and has no mechanism to run it. Add it when the runtime liveness decision (#1) resolves; until then the honest statement is that this is a manual review, and The Board's System lane will show it aging.
