## ⚠ Slack routing gap found — affects every Mac-side loop, not just this one
The loop line **could not be posted to `#yourco-david`**: `chat.postMessage` returned `not_in_channel`. Cause,
verified via `auth.test` + `conversations.list`: the token in `runtime/.slack.env` is the **`Reed`** bot
(`B0B8VNG3095`), and it is a member of exactly **two** channels — `#all-yourco` and `#yourco-Reed`. It is in
**none of the other 25 `#yourco-*` agent channels** (`#yourco-david` = `C0BAAGJUY3D`, `is_member=False`).

This is the failure mode `runtime/slack-channels.md:69` already warns about — "an uninvited channel silently
drops the post" — and it is silent by construction: `post_slack()` returns `False` and no caller checks the
return value. So **any Mac-side loop posting to its own agent channel has been dropping its line with no
error surfaced.** (The VPS may hold a different token — this finding is scoped to what is on the Mac.)

- **Delivered instead:** posted to `#all-yourco`, the fallback `slack-channels.md:69` explicitly names, with
  the reason stated in the message so the gap is visible rather than silent.
- **Fix is the Founder's, in Slack** — the documented host step, per channel: `/invite @atlas` (or this bot), then
  `sudo systemctl restart yourco-slack-listener`. **This loop cannot self-serve it:** the token's scopes are
  `channels:read, chat:write, chat:write.customize, files:write, channels:history` — no `channels:join`, and
  no `groups:read` (so private channels are invisible to it too).
- **Worth a `post_slack()` hardening pass** so a dropped post raises instead of returning `False` unchecked —
  that is what made a 25-channel gap invisible until a loop happened to look.

## ⚠ Second finding — the mandated CRM write path churns the whole file
The first commit of this run (`afd7460`) came out **365 changed lines for a 12-line append**. No data was
harmed — the diff was `"—"` → `"—"` on every non-ASCII string in the file — but the cause is a real
inconsistency in the shared write path:

- `dashboard/melanie.py` `_atomic_dump()` (line 592) and `write_mirror()` (line 555) call `json.dump` /
  `json.dumps` **without** `ensure_ascii=False`, so they escape every em-dash, `·` and arrow.
- **Thirteen other CRM writers pass `ensure_ascii=False`** — `crm/mirror.py`, `crm/autonomy.py`,
  `crm/adversarial.py`, `crm/promises.py`, `crm/integrations/instantly_sync.py`, `runtime/crm_hygiene.py`,
  `runtime/promote_intent.py` and others — and they are what left the file in literal-UTF-8 form.

So the encoding form **flip-flops with whichever writer touched `data.json` last**, and each flip is a
~360-line diff on `data.json` *and* `data.js`. That is precisely the churn that buries a real change — the
failure mode `runtime/commit-scoped.sh` exists to prevent, arriving through the file's own write path.

- **Handled in-run:** rewrote both files in the majority form (`ensure_ascii=False`, byte-identical data,
  verified `before == after` on a `sort_keys` dump and `62 passed, 0 failed`), so this run's net change against
  the pre-loop state is **12 insertions, 1 modification** — the activity and Partner B's `lastTouch`, nothing else.
- **Root fix NOT applied — deliberately out of scope.** It is a two-argument change to `melanie._atomic_dump`
  and `melanie.write_mirror`, but those are the canonical write path for `crm/server.py` (the live UI),
  `crm/connector_writes.py`, `runtime/site_intake.py` and `runtime/crm_hygiene.py`. `dashboard/melanie.py` is
  also outside this loop's committed path, so changing it here would break the scoped-commit contract. **the Founder's
  call** — recommend adding `ensure_ascii=False` to both, which makes melanie agree with the other 13 writers
  and ends the flip-flop. Until then every melanie-path write re-escapes the file.
